Goal and running order 20 minutes

The opener sets the end goal of the upskill and earns the agent harness. In 20 minutes, trainees learn what they'll build and the exact problem it solves, and see from their own runs what one LLM call can't do, what a LangGraph pipeline adds around it, and what that costs. Hands-on is copy-paste: trainees paste the provided TODO snippets and try the four requests. Everything that doesn't fit is either a trainer demo or in the hands-on sheets' After the session sections.

By the end, trainees can

  • State the problem statement and the four requests that define done
  • Explain what one LLM call does well (the creative part, rules that are written down) and what it can't do (memory, photos, sizes, rules nobody wrote down)
  • Explain what a LangGraph pipeline adds (state, a checkpointer, a router, a review loop), where it stops, and what its retries cost
  • List the requirements that lead to an agent harness

Before the session

Every trainee needs

  • Python 3.12 or newer, and uv
  • git, and access to the KeyValue repo
  • A coding agent they already use: Cursor, Claude Code, or another
  • A key for KeyValue's LiteLLM proxy: LITELLM_API_KEY and LITELLM_BASE_URL in .env

Ask trainees to run uv sync and cp .env.example .env, add their key, run uv run python -m launchkit.check_setup until it says Setup complete, then add LAUNCHKIT_IMAGES=placeholder to .env and check out session-01-llm-call. A real image takes about a minute through the proxy and the four requests make four of them, which the short hands-on can't absorb. Keep real images on your own machine for the demos.

Trainer checklist

  • On session-01-langgraph, with a real key: the LLM call handles R1 but not R2–R4; after pasting the four LangGraph TODOs, all four requests work, in under a minute with placeholders
  • check_setup passes, including the image check, so the key reaches gpt-4.1-mini and gpt-image-1 through the proxy
  • Asked the proxy admin about intermittent 401 errors (Incorrect API key provided: sk-svcac…). In dry runs up to 1 in 4 requests failed this way; it's the proxy's upstream key, not the trainee's
  • Rehearsed the three live runs below on your own machine: the starter on session-01-llm-call, the festival brief after the LLM-call TODOs, and the festival brief on session-01-langgraph after TODO 4
  • Checked the cost line on slide 8 against your graph.py: it assumes the reviewer runs after every write (2 calls for a clean poster, 4 with one retry)
  • Pairs arranged: one drives, one navigates
  • Slides open in full screen (press F)

Three ways to run things

CommandUse it for
uv run python -m launchkit.ask R1One request. Prints every model call (what was sent, what came back), the poster, Harbor's rules checked and the images. Add --approach graph on the LangGraph branch, and --no-image to skip the paid image call.
uv run python -m launchkit.uiThe same in a browser, at http://localhost:8000. Harbor's four requests are one click away, and it remembers each conversation, so R1 then R2 works as a follow-up. Pick LangGraph under Approach on the LangGraph branch.
uv run python -m launchkit.scoreboard --approach llmThe quickest way to try all four requests: runs them in order and says which work, with a reason for each. Use --approach graph on the LangGraph branch. It's a terminal tool only; the slides don't show scores.

The repo runs on the real model. Results vary from run to run, which is itself a teaching point; complete() deliberately skips the proxy's reply cache so that they do. A real image takes about a minute through the proxy.

Kickoff

Title and agenda · slides 1–2

Walk the agenda in one breath. The thread: every segment opens on the request the last one left failing, and ends on a new one. Two checkpoints: CP1.1 (the harness) and CP1.2 (grounded copy).

LaunchKit, Harbor and its brand pack · slides 3–4

Say: LaunchKit is a marketing assistant platform. A brand describes a concept and gets finished posters back. By the end of the upskill, each pair builds its Poster Ad agent, combining five skills.

  • Slide 4: Harbor's launch is around forty poster variants. Rules, words, sizes and iteration are what make it hard.
  • Harbor's rules are concrete and checkable by code: word limits, banned claims, placement sizes. Point out what the brand pack can't list: every claim Harbor has never made, like "survives drops". It comes back in both debriefs.

The problem and the four requests · slide 5

  • Read the problem statement aloud. Walk R1–R4 in the table: a concept becomes a poster, a follow-up edit, a photo, a resize of that poster. "Passes when" decides, not opinions.
  • Show of hands: how many of the four can one LLM call handle? Remember the answer for the debrief.

One LLM call

How it works, live · slide 6

  1. The grey line under the heading is the whole approach: a prompt with Harbor's rules, one call, parse the text, the image model gets the picture description only, and plain code resizes.
  2. Run the starter: uv run python -m launchkit.ask R1 --no-image on session-01-llm-call. The model writes a decent poster idea, but as prose, so code gets no JSON object in the model's reply; in the dry run it also invented a tagline, "Stay Fresh. Stay Tidal." Walk the four numbered problems on the slide. That's what TODO 1 fixes.

Don't promise the room broken word limits or banned words. Once the rules are in the prompt, gpt-4.1-mini followed every written rule in all 51 dry-run posters. The failure worth showing is the rule nobody wrote down.

Debrief: what one call can't do · stay on slide 7

  • Compare with the show of hands. One call can't remember the conversation (R2), use a photo (R3) or resize "that poster" (R4).
  • Run the festival brief live: uv run python -m launchkit.ask --no-image "Summer festival poster: the Tidal bottle survives being dropped on concrete and keeps water ice cold all day." The rules check says ✓, yet the copy claims something like "Ready for any drop" (4 of 5 dry runs). Harbor never said that, and bans "unbreakable". Ask: what would catch it?

A LangGraph pipeline

How it works, live · slide 8, the diagram

  1. route, then write → check → picture, with a retry loop from check back to write, give_up after two tries, and a resize branch that uses no model. write is the LLM call they just finished.
  2. State is one dict every node reads and adds to; a checkpointer keeps it per conversation (thread_id). The graph decides what runs next, never the model.
  3. Leave the two red strips for the debrief; go back to slide 7.

Debrief: where the graph stops, and what it costs · slides 8–9

  • Run the festival brief live with the graph: uv run python -m launchkit.ask --approach graph --no-image "Summer festival poster: the Tidal bottle survives being dropped on concrete and keeps water ice cold all day." Point at the reviewer's => UNSUPPORTED line and the second write call carrying "Fix these problems". In the dry run: drop claims in 4 of 5 posters before TODO 4, 0 of 8 after. The loop doesn't trigger on every run; if it doesn't, run it again.
  • Slide 8, left strip, It doesn't scale: R4 alone needed a router node, a resize node and a router prompt, and every new kind of request means more of the same.
  • Slide 8, right strip, It costs more: the retry and the review loop buy quality with more model calls. A clean poster is a write and a review; one retry doubles that, to 4. Ask the room what happens to cost and latency when Harbor asks for 40 posters (up to 160 calls), and how they'd cap it. The reviewer is a model too: on a test set it let 3 of 12 bad claims through. What checks the checker?
  • Slide 9: read the requirements out. The model chooses the next step, code enforces limits, actions are tools, state is shared, output is validated, and per-brand rules live with the brand.

Close and likely questions

Bridge (slide 9). The last line of slide 9 says it. Say: "That set of requirements has a name: an agent harness. Next, we let the model choose its next step, inside limits our code enforces, on Agno." Then advance to slide 10, the agent loop.

Likely questions

"LangGraph can build agents too, can't it?"
Yes. The point is which responsibilities you still build yourself: per-brand instructions, skills, memory, limits and validation. The next segment names them.
"Wouldn't a better model just get it right?"
It reduces bad output, but no model can see a conversation it isn't given, use a photo it isn't sent, or resize a file it can't reach. As a reviewer, gpt-4.1 scored 22 of 24 against gpt-4.1-mini's 21.
"Isn't the review loop just doubling the bill?"
On a retry, yes: that's the trade on slide 8. The harness segment adds budgets and limits, so quality checks can't quietly multiply cost.
"Why did my results differ from my neighbour's?"
The model isn't deterministic. That's one more reason code checks every reply.
"Why does the router ask two questions?"
One question kept misrouting requests. Let the model answer small questions; let code make the decision.
"Why did R2 make a whole new picture just to shorten the headline?"
Every edit goes through picture. Reusing the last picture for copy-only edits is the first stretch task.
"Why not let the image model draw the text?"
Image models misspell and can't follow brand fonts or safe zones, and words in pixels can't be resized to other placements. Code renders the text later (the supers skill).
