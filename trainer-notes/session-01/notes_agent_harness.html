Session 1 · Building a mini-Pencil

The agent harness, and the workspace as its home

Notes for the talk and discussion at 0:18–0:38. They cover what an agent harness is, what Agno gives you, and how a folder of plain files can shape an agent's behaviour, with Pencil as the real-world example throughout.

  • About 25 minutes to read
  • Hands-on comes later, in the harness part of guide step 7

Every concept below follows the same five parts, so you can skim the first and stop, or read all five:

  • In plain terms: the idea in a sentence or two.
  • Why it matters: what goes wrong for LaunchKit without it.
  • How it breaks: the failure you'll actually see.
  • Example: a small piece of code or a diagram.
  • How Pencil does it: what a production system chose, and what it cost.

Discussion questions appear where they come up in the session. Try answering before you open the suggested answer.

The running example

LaunchKit, Harbor and Ember Coffee Co. are fictional.

We're building LaunchKit, a marketing assistant. Its first job: turn one campaign concept into on-brand poster ads. The first customer is Harbor, launching an insulated bottle called Tidal. A second customer, Ember Coffee Co., arrives later and needs a different voice and different rules.

A poster has a short headline, a subheadline, body copy and a picture. Harbor's rules include word limits (headline up to 6 words, subheadline up to 12, body up to 25) and a list of claims the copy must never make, such as "eco-friendly".

The opening demo of this session sent Maya's four requests, in order, in one conversation, first to one AI call and then to a LangGraph pipeline:

Maya saysWhat happened
R1 · "Tidal launch, a misty lakeshore at dawn. Can I get a concept, a storyboard, the words and a poster?"One AI call: a chat reply, not a form. It made up a tagline and ended with a question. With a fixed answer shape and four calls (concept, storyboard, words, poster), it passes.
R2 · "Love it. Just the story size now, please."One AI call: the code ran every step again and drew a new picture. LangGraph: a saved state and a router send it to a resize path, so the approved picture stays.
R3 · "What does your brand book say about washing the lid?"One AI call: a new poster instead of an answer. LangGraph: forced onto the nearest path, until someone draws one more path for questions.
R4 · "Is the lid dishwasher-safe? If not, fix the copy, then give me the story size."Both: the code can take only one path. Two of the three asks vanish, and nobody tells her.

These notes pick up from there.

Part A · 0:18–0:30

The agent harness, and Agno as the engine under it

A1Why a model alone isn't a product

A model call takes text in and gives text back. It doesn't remember the last request, check its own work, follow your rules reliably, or do anything in the world.

Why it matters

Everything a marketer needs from LaunchKit sits outside that one call: the poster spec in a fixed shape, the banned claims kept out, the picture generated without words baked into it, and the follow-up that remembers which poster we're talking about. The model is a powerful part, but it's one part.

How it breaks

What we sawWhat was missing
A chat reply, not a form (R1)A typed output that's validated
"Just the story size" drew a new picture (R2)State that survives to the next message
A question got a new poster (R3)A way to choose the next step from what was asked
Three asks in one message, two lost (R4)A loop that can take more than one step, and limits around it

How Pencil does it

Pencil's assistant, Scribble, makes the agent name its final deliverable explicitly, and retries a blank answer once before showing an error. Neither comes from the model. Both are code around it.

A2Three ways to put a model to work

There's a spectrum. At one end, you call the model once. In the middle, you wire calls into fixed steps you drew in advance (a workflow). At the other end, the model decides the next step itself, in a loop (an agent).

Plain callWorkflow (fixed graph)Agent loop
Who picks the next stepNobody: one stepYour code, decided in advanceThe model, at run time
Good forRewrite this line; classify this textWork with a known shape: resize 500 images every nightRequests you can't predict: "three variants", "just resize", "use my photo instead"
Breaks whenThe task needs more than one stepA new kind of request arrivesNothing bounds it: loops, cost, wrong tools
PredictabilityHighHighLower; needs limits

Why it matters

A fixed graph like the LangGraph pipeline in the demo is a good tool when you can draw the flow in advance. It handled the happy path well. It broke because LaunchKit's requests can't be drawn in advance: every new kind of request needs another node and another edge, and retries are written by hand for each step.

Agents aren't free. They're less predictable, usually slower and more expensive, and harder to test. Start with the simplest thing that works and move right along the spectrum only when the requests demand it.

How it breaks

Adding nodes for every new request is the obvious fix to the graph, and it fails for a real reason: the number of request shapes keeps growing, and each one needs a developer.

Discuss · 1

Where would you still use a fixed graph instead of an agent loop?

Suggested answer

When the steps are known and stable, mistakes are expensive, or you need the same path every time for audit: a nightly batch resize, a compliance check that must always run in the same order, a data pipeline. Many real systems mix both: an agent that calls a fixed workflow as one of its tools.

A3What an agent harness is

An agent harness is everything around the model that makes it reliable. The model proposes; the harness enforces.

The name fits: a harness channels the power of something strong and unpredictable in a useful direction. Letting the model choose its next step fixes the rigidity of the graph, but now it can loop forever regenerating "a better sky", lose track of what it was doing, call tools it shouldn't, or return anything at all. The harness is what stops that.

Harness: our code

limitstool dispatchinstructions and contextstateoutput validationidentity
Agent loop: model ↔ tools (the engine, Agno)

Why it matters

You need this layer whichever framework sits underneath, because it's where your product's rules live. A framework can run a loop; it can't know that Harbor bans "eco-friendly", that a turn may spend at most three image generations, or which customer is asking.

A4The agent loop, step by step

The model never runs anything itself. It replies with either a final answer or a request to call a tool. The harness runs the tool, feeds the result back, and asks again, until there's a final answer or the harness decides to stop.

Build contextInstructions, history, the request
Call the modelIt returns text or tool calls
Check the callExists? Allowed? In budget? Valid args?
Run the toolFor example, render_image
Feed back the resultAppend it, then loop
Stop and validateFinal answer or a limit hit

Dark boxes are where the harness decides. Light boxes are the model and the tools.

Example: "Give me three variants"

StepModel proposesHarness does
1Call write_spec three times with different anglesRuns them; validates each spec
2Call render_image for each specChecks the image budget (3 per turn); runs them
3Final answer: three postersValidates the output; returns a typed result

Nobody drew a "three variants" node. The model chose the steps; the harness kept them inside the rules.

How it breaks

  • It never stops, regenerating the same image to "improve" it.
  • It calls a tool that doesn't exist, or that it isn't allowed to use.
  • It retries a failing call with slightly different arguments, again and again.
  • Its final answer is malformed.

Each of these is caught by a different part of the harness, covered next.

Discuss · 2

Model or code? Sort these: the next step, the step limit, which tool to call, the user's identity, the headline wording, the image budget.

Suggested answer

Model: the next step, which tool to call, the headline wording. Code: the step limit, the user's identity, the image budget. The rule of thumb: the model makes choices that need judgment; code enforces anything about safety, money, identity or correctness that you can check.

A6Limits

Limits are how the harness stops a loop that has gone wrong. There are several kinds, and each catches something the others miss.

LimitCatchesMisses
Step cap (max tool calls per turn)Runaway loopsCuts off a long task that was doing real work
Time limits, nested: per tool, no progress, whole turnHangs and slow toolsA fast loop that finishes within time but goes nowhere
Per-tool breakerThe same tool failing again and againCalls that succeed but go nowhere
Budgets for paid callsCost: the 4th image generation when the budget is 3Loops that cost nothing

One detail matters for the breaker: count failures by the tool's name, not its arguments. A model stuck on a broken tool tends to retry with slightly different arguments each time. A counter keyed on the exact call never fires.

Example: an image budget as a tool hook

Agno lets you wrap every tool call in a hook. The hook gets the tool's name, the function and its arguments. Calling the function runs the tool; returning without calling it blocks the tool, and whatever you return becomes the tool result the model sees.

def image_budget(function_name, func, args):
    if function_name == "render_image":
        if turn.images_used >= 3:
            return "Refused: this turn's image budget (3) is used up."
        turn.images_used += 1
    return func(**args)

agent = Agent(..., tool_hooks=[image_budget], tool_call_limit=6)

tool_call_limit is Agno's built-in step cap. In the hands-on we use 6.

How Pencil does it

One Scribble turn made about 50 calls to a search tool over about 14 minutes. The search skill kept telling the model to call a different search tool that wasn't available in that workspace, and the model kept obeying. A sibling turn finished in under 17 seconds, so the problem depended on the model's choices, not on the code path.

Pencil's fix was a breaker, not a step cap. Failures are counted per tool name, ignoring arguments:

  • From the 2nd failure, a nudge is added to the tool result.
  • At 3, that tool is disabled for the rest of the turn.
  • At 12, the turn ends, in the strict mode only. The default mode disables the tool and lets the turn continue.

Around it sit nested time limits: one tool call can take up to 30 minutes, a turn with no progress for 40 minutes is failed, and no turn runs longer than an hour. Paid image and video generation is checked against the customer's credit before each call.

Gained: long, legitimate turns aren't cut off by a fixed count

Cost: only known kinds of failure count, so calls that succeed but go nowhere run until the time limit

Discuss · 3

The hands-on uses a step cap of 6. Why didn't Pencil use one?

Suggested answer

Scribble's real turns vary enormously: a quick reply might take one call, a multi-asset campaign might take dozens of legitimate ones. Any fixed number would either cut good turns short or be too high to catch anything. The incident showed the real danger was one broken tool repeated, so Pencil limits that directly, and backs it with time. For a small, predictable agent like LaunchKit's, a step cap is simple and fine.

A7Output contracts

The harness defines exactly what a finished answer looks like, checks it in code, allows one repair, and otherwise returns a clear error.

Why it matters

Downstream code (the image model, the layout, the marketer's screen) needs a predictable shape. "The model usually returns JSON" isn't a contract.

Example

class PosterSpec(BaseModel):
    headline: str        # 6 words or fewer
    subheadline: str     # 12 words or fewer
    body: str            # 25 words or fewer
    image_prompt: str    # the picture only, never the words

def check(spec, brand):
    errors = []
    if len(spec.headline.split()) > 6: errors.append("headline over 6 words")
    for claim in brand.banned_claims:
        if claim in spec.body.lower(): errors.append(f"banned claim: {claim}")
    return errors

Agno can ask the model for this shape directly with output_schema=PosterSpec. Your check still runs, because a schema checks the shape, not the rules. If check fails, send the errors back for one repair. If it fails again, return a typed error. Invalid copy never reaches the image model.

How it breaks

Without a repair limit, a model that can't satisfy a rule repairs forever. Without a typed error, failures show up as half-finished posters.

How Pencil does it

Scribble's agent ends a turn by calling a deliver_final tool that names its final outputs. After that, further tool calls are refused, which stopped agents from carrying on with checks after they'd already delivered. A blank answer is retried once, on the same model; if it's still blank, the user sees an error and isn't charged. The team chose not to switch models on retry, because "a silent swap makes the reply's provenance a lie".

A8State

State is what lets the next message build on the last one. Three things are easy to confuse: the transcript (everything said, stored), the session (one conversation's identity and data) and the context window (what the model actually sees on this turn).

Why it matters

"Just the story size" only works if the harness loads the earlier turns about that poster. But you can't send the whole transcript forever: it gets slow and expensive, and important instructions get buried.

Example

agent = Agent(
    db=sessions_db,                 # where transcripts are stored
    session_id=conversation_id,     # set by the harness, never by the model
    add_history_to_context=True,    # without this, history isn't sent
    num_history_runs=5,             # only the last 5 turns go to the model
)

How it breaks

  • No session: every message starts from scratch.
  • Unbounded history: every turn costs more than the last.
  • A session id taken from the request: one user can read another's conversation.

How Pencil does it

Scribble keeps the full transcript per conversation in a database and sends only the last five turns to the model. Session ids come from the system. Managing long histories (summaries, trimming bulky tool results) is a Session 2 topic.

A9Model abstraction

Every model sits behind one interface. Code asks for a model by a string such as "provider:model", and the same retry and timeout policy applies to all of them.

Why it matters

  • You can pick a model per task (a fast one for copy, a strong one for planning) without rewriting the harness.
  • You can swap in a fake model in tests: one that returns a valid spec, one that returns malformed output, one that never stops. That's how you test limits and repairs without paying for, or waiting on, a real model.

How it breaks

Quiet fallbacks change behaviour without anyone noticing. If the model you asked for isn't available and the system silently uses another, the output changes and nobody knows why.

How Pencil does it

Scribble turns one model string into an Agno model in a single place. Which models a customer may use is a policy: if the requested model isn't enabled, Scribble falls back to the customer's best enabled model, choosing availability over exactness. For blank-answer retries it deliberately does the opposite and keeps the same model (see A7). Both are product decisions, made in the harness.

A10Agno, the engine under the harness

Agno is an open-source Python framework for building agents. It works with many model providers. It gives you the generic machinery, so your code can focus on the product.

What Agno gives you

  • Agent: the loop, with instructions, a model and tools.
  • Tools: plain Python functions (or ready-made toolkits, or MCP servers) with their schemas generated for the model, plus tool-call parsing for each provider.
  • Sessions: stored conversations and history.
  • Memory and knowledge: hooks for retrieval (the brand book part of this session) and long-term memory (Session 2).
  • Teams: several agents working together (Session 2).
  • Controls: tool_call_limit, tool_hooks, output_schema, and exceptions a tool can raise to retry or stop the run.

Example: LaunchKit's agent, roughly

from agno.agent import Agent

agent = Agent(
    model=make_model("provider:model"),           # our helper: one interface
    instructions=build_instructions(workspace),   # from the brand's files (Part B)
    tools=[write_spec, render_image, resize_image],
    output_schema=PosterSpec,                     # typed result (A7)
    tool_call_limit=6,                            # step cap (A6)
    tool_hooks=[image_budget],                    # budget (A6)
    db=sessions_db, session_id=conversation_id,   # state (A8)
    add_history_to_context=True, num_history_runs=5,
)

Illustrative only: you'll build the real one in the hands-on. Notice how many of the arguments are harness decisions passed into the engine.

Part B · 0:30–0:38

OpenClaw on Agno: the workspace as the agent's home

B1Configuration as files

Put an agent's behaviour (its persona, rules and memory) in plain text files, one folder per agent, instead of in code.

Why it matters

  • No deploy: change a file and the next turn changes.
  • Readable: a marketer can see exactly what the agent is told.
  • One per customer: a new brand is a new folder, not new code.
  • Versioned: files can live in git, so every change is reviewable and reversible.

B2The OpenClaw workspace

OpenClaw, an open-source agent runtime, popularised a simple convention: each agent has a workspace folder that is its home. A handful of files with fixed names and roles define who the agent is and how it works.

FileRoleWhen it's read
AGENTS.mdOperating instructions, and how to use memoryEvery session
SOUL.mdPersona, tone and boundariesEvery session
USER.mdWho the user is, how to address themEvery session
IDENTITY.mdThe agent's name and styleSet up on first run
MEMORY.mdCurated long-term memoryOnly in the main, private session
memory/YYYY-MM-DD.mdA daily logRecent days at start; older ones on demand
BOOTSTRAP.mdA one-time first-run ritualOnce, then deleted
skills/Workspace-specific skillsWhen needed

Two details from OpenClaw's docs worth knowing. First, files injected into the prompt are truncated: 20,000 characters per file and 60,000 in total by default. Second, the workspace is the agent's default working folder, not a hard sandbox: without sandboxing turned on, tools can still reach the rest of the machine.

LaunchKit uses a subset: SOUL.md, AGENTS.md, MEMORY.md, memory/ and skills/, one folder per brand.

workspaces/
├── harbor/
│   ├── SOUL.md        # calm, outdoorsy
│   ├── AGENTS.md      # word limits; never "eco-friendly"
│   ├── MEMORY.md
│   └── skills/
└── ember/
    ├── SOUL.md        # warm, crafted
    ├── AGENTS.md      # + Never use the word "cheap"
    ├── MEMORY.md
    └── skills/

Put this convention on top of Agno's engine and every brand gets its own agent by changing files, not code. Agno stays the engine; the files shape what it's told.

B3Files into instructions

The harness reads the workspace's files and assembles them into the model's instructions: in a fixed order, each within a size limit, with the stable parts first.

Example

def build_instructions(ws):
    parts = []
    for name in ["SOUL.md", "AGENTS.md", "MEMORY.md"]:   # stable first
        text = ws.read(name) or f"# {name}\n(missing)"
        parts.append(text[:MAX_CHARS_PER_FILE])           # cap each file
    return "\n\n".join(parts)

Why the order and the caps matter

  • Order: model providers can cache the start of a prompt that doesn't change between turns. Keep what rarely changes (persona, rules) first and what changes often (memory, the user) last.
  • Caps: without them, one huge file crowds out everything else and makes every turn slow and expensive.

How it breaks

A cap that cuts silently can drop the one rule that mattered. A missing file can produce an agent with no persona. Make both visible: mark truncation and missing files in the instructions and in your logs.

B4Identity picks the folder

The harness works out which workspace to read from who is signed in. The request never names the folder, and the model never chooses it.

Signed-in user→ Their brand's folder→ Instruction builder→ Harness

Why it matters

This is the fix for the brand=harbor leak. If the path to the folder comes from the request, or from anything the model writes, someone will eventually point it at another customer's files.

How it breaks

  • A workspace name read from the request body.
  • A path built from user input without checks (../harbor).
  • One shared folder for every brand, filtered "by convention".

How Pencil does it

Scribble takes the user and workspace from a signed login token and checks membership before doing anything. A worker serves exactly one workspace at a time. Per-user files are found from the signed-in user's id, and there's no function that accepts someone else's id, so reading another user's file isn't possible by construction.

B5Who edits what

Once behaviour lives in files, someone has to decide who may change each one.

EditorWhat they might changeThe risk
The marketerTone, rules ("never say cheap")A rule that conflicts with another, or with the law
The agent itselfMemory, notesDrift: the agent slowly rewrites who it is. A malicious instruction in a document gets saved and obeyed forever
An engineerThe harness codeThe bottleneck we were trying to remove

How Pencil does it

Pencil splits it. The persona and start-up files (SOUL and BOOT) can only be edited by an admin; the agent can't change them. The agent can write memory, but saving a memory that applies to the whole workspace needs the user to confirm it.

Discuss · 4

Who may edit a workspace's files: the marketer, the agent itself, or an engineer? What goes wrong with each?

Suggested answer

There's no single right answer, but most teams land on a split like Pencil's: humans own identity and rules, with review; the agent owns notes and memory, with confirmation for anything shared; engineers own the harness. The question to ask of any file: if it changed silently tonight, who would notice?

B6How Pencil does it

Pencil keeps the workspace idea but loads less of it into every prompt. Each Pencil workspace has its own set of files, which Pencil calls its DNA.

FileLaunchKit (what we build)Pencil
SOUL.mdPersona and tone; loadedLoaded first. Admin-only
BOOT.mdNot usedA start-up protocol; loaded second. Admin-only
AGENTS.mdOperating rules; loadedA list of the workspace's sub-agents, generated automatically. Kept out of the prompt; the agent searches for what it needs
MEMORY.mdCurated memoryA short index of memories, loaded last. Each note is cut to a short summary; details are fetched on demand
Per-user fileNot usedOne per user, found from the signed-in user
  • New workspaces start from preset files.
  • Editing a workspace's files rebuilds its cached agent, so the change lands on the next turn.
  • Operating rules live in SOUL and BOOT, not in AGENTS.md: Pencil uses the same file name for a different job.

Gained: every workspace behaves differently with no deploy

Cost: deciding who may edit what, and how much rides in every prompt

Discuss · 5

What belongs in workspace files, and what must stay in code? And what should be looked up when needed, rather than loaded every time?

Suggested answer

Files: tone, rules, memory, skills: anything a brand owns and might change. Code: limits, identity, validation, permissions: anything that keeps the system safe and correct whatever the files say. Looked up: anything large, rarely needed, or different per request, such as the full sub-agent list in Pencil, and as you'll see next, product facts.

Check yourself

1. In one sentence, what's the difference between a workflow and an agent?

In a workflow, your code decides the next step in advance; in an agent, the model decides it at run time, inside limits your code enforces.

2. Name four jobs of a harness that a framework can't do for you.

Any four of: deciding your limits and budgets, enforcing your brand rules, knowing who the user is and what they may touch, choosing which model a task uses, deciding what happens on failure.

3. Why should a breaker count failures by tool name rather than by exact call?

A model stuck on a broken tool retries with slightly different arguments. Counting exact calls never reaches the limit.

4. A schema validates your poster spec. Why do you still need a rule check?

A schema checks the shape (fields and types). It doesn't check word counts or banned claims.

5. What's the difference between the transcript and the context window?

The transcript is everything said, stored. The context window is the part the model sees on this turn, such as the last five turns.

6. Why must the workspace be picked from the login and not the request?

Anything in the request can be changed by the user, so a user could point it at another customer's folder.

7. Why keep stable files first when building instructions?

Providers can cache an unchanged prompt prefix, making turns faster and cheaper. Changing parts go last.

8. Why doesn't pasting the whole fact sheet into AGENTS.md fix "dishwasher-safe"?

A size cap cuts the file and can drop the line that matters; without a cap, every turn carries every fact, which is slow, costly and buries the important line.
